图片压缩上传

10MB 的照片，压成几百 KB 再传
👀 日常场景

发帖时选了张手机拍的 10MB 原图，上传进度条却“嗖”地一下走完了。你以为网速飞起，其实是浏览器在上传前先把照片压小了——传的只是几百 KB 的压缩版，肉眼还看不出差别。

原理：它是怎么运作的

💡 用 canvas 把图片按尺寸和质量重绘，导出为压缩后的 Blob 再上传，大幅减小体积且肉眼几乎无差别。

先看全过程

  1. 用户选择本地图片
  2. 读入并解码为图像
  3. canvas 按比例缩放重绘
  4. 按质量导出压缩 Blob
  5. 上传压缩后的文件
  6. 展示压缩前后对比

手机拍张照片动辄 8～10MB，直接上传又慢又费流量，但其实发帖、头像这种场景根本不需要原图。浏览器的 canvas 就是免费的“压缩车间”：把图片画到 canvas 上（drawImage），可以指定缩小后的尺寸（比如最长边压到 1920px），再用 canvas.toBlob(blob => ..., 'image/jpeg', 0.8) 导出——第三个参数就是质量，0.8 左右肉眼几乎看不出差别，体积能压到原来的 1/10。整个过程在用户手机上完成，传的只是几百 KB 的小文件，所以“上传秒完成”的真相是“传之前先压好了”。几个实战坑：一是 iOS 照片的 EXIF 方向信息：手机横着拍照存的可能是竖图加旋转标记，直接画 canvas 会 sideways（方向不正），得先读 EXIF 摆正；二是 PNG 转 JPEG 会丢透明通道，透明底变黑底，头像场景要注意；三是大图压缩放主线程会卡界面，几 MB 以上的图建议扔 Web Worker 里压。跟服务端压缩不冲突：前端压是省带宽和时间，服务端压是统一规格，两边都做最稳。

网站是怎么做到的

  • canvas：免费的压缩车间：浏览器把图片画到 canvas 上再导出，指定缩小尺寸和质量（0.8 左右），体积能压到 1/10，肉眼几乎看不出差别。
  • EXIF 摆正：iOS 照片的方向陷阱：手机横着拍照，存的可能是竖图加一个“旋转标记”。直接压缩会 sideways（方向不正），得先读标记摆正。
  • PNG 转 JPEG 会丢透明：JPEG 没有透明通道，透明底会变成黑底。头像、logo 这种带透明的图要当心。
  • Web Worker：别卡死页面：大图压缩是重活，放主线程页面会卡死几秒。扔给 Web Worker 在后台压，用户无感知。
  1. 你选了一张 10MB 的手机原图
  2. 浏览器先读 EXIF，把照片方向摆正
  3. 按最长边（比如 1920px）等比缩小，画到 canvas 上
  4. 按 0.7～0.8 的质量导出成几百 KB 的新图片
  5. 上传的其实是这个压缩版，所以进度条“嗖”地走完
  6. 肉眼看：和原图几乎没差别，体积只剩 1/10
