数据库连接池

建一次连接，复用一万次
👀 日常场景

每次查数据库都要先 TCP 握手、再登录认证，握手一次要几十毫秒——高峰期每秒上万次查询，光握手就能把数据库拖死。连接池提前建好一批连接放着，用完归还，下次直接复用，握手的开销一次就够了。

原理：它是怎么运作的

💡 预先建立一批数据库连接反复复用，省掉每次 TCP 握手与认证的开销。

先看全过程

  1. 应用启动时建好 N 个连接
  2. 业务需要时从池里借一个
  3. 用完立即归还到池中
  4. 池空了：排队等待或扩容
  5. 空闲太久：关闭回收
  6. 应用关闭：优雅释放所有连接

建一个数据库连接不便宜：TCP 三次握手、TLS（如果开了）、数据库的认证授权、分配会话内存，加起来几十毫秒。高并发下如果每次查询都现建连接，数据库光应付握手就满了——这就是连接池存在的理由。

池的核心参数就三个：最小空闲连接（保底）、最大连接数（上限）、获取超时。最大连接数不是越大越好：数据库的连接数对应着内存和线程，MySQL 默认才 151 个，应用开 500 个连接只会把数据库打爆。经验公式是「池大小约等于 CPU 核数 × 2」，再按压测调。

连接池还顺手解决了「连接泄漏」：借了不还的连接会被超时回收，配合监控能揪出没关连接的代码。云原生时代还有 PgBouncer 这类中间件池，让几千个应用连接复用几十个真实数据库连接。还有一个常见误区是把池建在错误的地方：Serverless 函数里每个实例都建一个池，实例一多连接数照样爆炸——这时应该用中间件池或 RDS Proxy 统一收敛。

开发者：应该如何接入

  • HikariCP：Java 界最快，以快和稳著称
  • Druid：阿里出品，自带 SQL 监控和防火墙
  • PgBouncer：PostgreSQL 专用中间件池
  1. 选连接池实现（别自己手写，坑比你想象的多）
  2. 配置 JDBC URL、账号密码（密码走环境变量/密钥管理）
  3. 设最大连接数：先按公式估，再压测微调
  4. 设连接超时和最大生命周期，防止僵尸连接
  5. 业务代码用完连接必须关闭（归还），推荐 try-with-resources
  6. 监控活跃连接数，持续打满就是扩容或优化 SQL 的信号
