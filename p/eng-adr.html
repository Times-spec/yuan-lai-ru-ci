ADR：给技术选型留的字条

给未来的自己留一张纸条
👀 日常场景

半年后新同事问：“为啥缓存用 Redis 不用 Memcached？”会议室一片沉默——当初记得“选了 A”，但没人记得“为什么没选 B”。ADR 就是回答这种问题的纸条：决策是什么、为什么、放弃了什么，一页写清。

原理：它是怎么运作的

💡 把重要的技术选型写成一页标准化文档（背景/决策/备选/后果），和代码一起版本管理，对抗团队的“决策失忆症”。

先看全过程

  1. 遇到重要技术选型或架构取舍
  2. 写 ADR：背景、决策、备选方案、后果
  3. 团队评审，记录不同意见
  4. 合并进仓库 docs/adr 目录
  5. 后人查代码时顺手看到决策上下文
  6. 决策变更时更新状态，不删历史

ADR（Michael Nygard 在《架构之美》中推广）解决的是“决策失忆症”：代码告诉你“是什么”，注释告诉你“怎么做”，但“为什么是这样而不是那样”——这个最有价值的信息，默认是丢失的。三个月后没人记得当初为什么放弃方案 B，于是有人“优化”回了 B，踩了当年已经踩过的坑。

一份 ADR 很薄，固定结构：标题、状态（提议/已采纳/已废弃）、背景（在什么约束下做决定）、决策（选了什么）、备选方案（考虑过什么、为什么没选——这是全文最有价值的部分）、后果（接受什么代价）。

存放位置是关键设计：放在代码仓库的 docs/adr/ 下，和代码一起做版本管理。决策变了怎么办？不删旧 ADR，把状态标成“已废弃”，再写一份新的——历史决策链本身就是财富。什么时候该写？经验法则：这个决定如果半年后有人问“为啥”，而你答不上来，就值得写。选数据库、选框架、拆服务边界要写；变量名怎么起，不用写。

团队该如何落地 ADR

  • 手写 Markdown：零依赖，一个模板走天下
  • adr-tools：命令行脚手架，自动编号和建模板
  • Log4brains：把 ADR 渲染成可浏览的知识库网站
  1. 在仓库建 docs/adr 目录，定一个 Markdown 模板
  2. 编号规则：0001-xxx.md 递增，标题说清决策
  3. 按模板写：背景、决策、备选、后果四段
  4. PR 评审 ADR，和代码评审同等对待
  5. 合并后状态标为“已采纳”，后续变更只追加不删除
