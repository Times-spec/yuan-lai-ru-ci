HTTP 302/303 临时重定向

这次先去别处看看，下次还来老地方
👀 日常场景

登录成功后页面一闪跳回首页；双 11 前夜官网临时换成“维护中，稍后再来”；同一链接每次打开看到的活动页都不一样。这些都是 302：它只管这一次，不管以后。下次访问，浏览器还是先去老地址问一问。

原理：它是怎么运作的

💡 服务端返回 302（或 303）加 Location 头，表示“这次临时去别处”，浏览器不缓存、搜索引擎不转移权重。

先看全过程

  1. 浏览器请求原地址
  2. 服务器返回 302 和临时地址
  3. 浏览器请求临时地址
  4. 下次访问仍先请求原地址
  5. 303 还会强制把请求改成 GET

302 的意思是“这次先去别处看看”。服务器返回 302 加 Location 头，浏览器会立刻去请求新地址，但和 301 不同，它不会把这次跳转记下来——下次访问还是先问原地址，搜索引擎也不会把权重转走。所以它适合一切“临时”的安排：登录成功跳回首页、网站维护时跳到维护页、同一链接按流量分流到不同活动页。还有个容易混淆的 303：它专治表单重复提交。提交订单后如果停留在 POST 的结果页，一刷新就会重复下单；于是有了 PRG 模式（提交-重定向-展示）：提交后服务端回 303，浏览器用 GET 去请求结果页，刷新多少次都安全。另外有个历史包袱：按规范 302 跳转应该保持原请求方法，但早期浏览器自作主张把 POST 改成了 GET，这个“将错就错”后来成了事实标准，也正是 307 被发明的原因。

🌀 如果没有它会怎样

没有 302/303，「这次临时去别处」就无从表达：维护页、登录回跳只能将就用 301——而 301 会被浏览器记下来、还会把搜索权重转走，临时安排变成永久伤害。

🚫 常见误解

302 跳转会保持原来的请求方法。规范确实这么写，但早期浏览器自作主张把 POST 改成 GET，还成了事实标准；真要保持方法，得用 307。

服务端该怎么配

  • Web 框架默认 redirect：Django redirect()、Express res.redirect() 默认就是 302
  • Nginx return 302：网关层一行配置搞定临时跳转
  • A/B 测试分流：按流量比例把用户 302 到不同版本页面
  1. 确认是临时行为（维护、登录回跳、分流），不是永久搬迁
  2. 在代码里调用框架的 redirect 方法，默认 302 即可
  3. 需要防表单重复提交时用 303（PRG 模式）
  4. 分流场景给 URL 加版本参数，便于统计区分
