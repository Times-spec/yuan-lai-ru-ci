AI 写的 Word 文档：数字和中文为什么像两种字体

同一行标题里，数字是 Calibri，中文是宋体
👀 日常场景

你让 AI 帮你写了份 Word 文档，打开一看标题不对劲：“2.3”这几个数字圆润现代，后面的“差异化定位”却带着宋体的衬线——像两种字体硬拼在一起。你把字删掉自己重打一遍，字形又统一了。是 AI 写错了字吗？不是。它写对了每一个字，只是“用什么字体画出来”这件事，在 Word 里比你想象的复杂。

原理：它是怎么运作的

💡 Word 给每个字符选字体时，会按“中英文”查两张不同的表；AI 生成的文档里，中文走的那张表指向了宋体。

先看全过程

  1. agent 写文档 = 拼 XML：docx 本质是个 ZIP，里面装着 XML，python-docx 只是在组装文本
  2. 标题样式不写具体字体名，写的是“主题字体”这种间接引用
  3. 主题文件里写死映射：西文 → Calibri，简体中文 → 宋体
  4. Word 渲染时按字符种类查表：数字走西文字体，中文走中文字体
  5. 于是同一行标题裂成两种字形：2.3 是 Calibri，差异化是宋体

先说结论：你的眼睛没骗你。那行标题确实被两种字体渲染了——“2.3”用的是 Calibri（圆润的无衬线体），“差异化定位与核心竞争优势”用的是宋体（带衬线的衬线体）。我把 python-docx 的默认模板拆开看过，又亲手复现渲染了一遍，证据确凿。

关键的第一步：Word 里“这段文字用什么字体”不是一句话，而是一套“按字符种类查表”的机制。OOXML 规范里，每个文字片段（run）的字体由 <w:rFonts> 标签的四个属性分别指定：ascii 管数字和英文字母，hAnsi 管扩展西文，eastAsia 管中日韩文字，cs 管复杂文字。Word 在画出每个字符之前，先看它落在哪个 Unicode 区间，再去查对应的那张表。

而 python-docx 默认模板里的标题样式，玩的是“间接引用”：它不写死“宋体”或“Calibri”，写的是“主题字体”——西文用主题的大标题西文字体（majorHAnsi → Calibri），中文用主题的大标题东亚字体（majorEastAsia）。主题文件 word/theme/theme1.xml 里，给每种文字都指定了默认字体，其中简体中文（Hans）对应的正是“宋体”。两条引用一分叉，字形就裂开了。

还有个十年老坑：很多人（包括 AI 生成的代码）会写 run.font.name = '微软雅黑' 来设字体，但这行代码只改 ascii 和 hAnsi 两个通道，生成的 XML 里根本没有 w:eastAsia——中文部分完全不受影响，继续走样式和主题的回退。你以为设置了字体，其实只设置了一半。

顺着这条线，就能回答“agent 写 Word 文档的底层原理是什么”：agent 从头到尾没有调用 Word，也没有排版引擎。它做的事分三步：生成 Python 代码 → 代码在内存里拼出 XML 树 → 打包成 zip（把 .docx 后缀改成 .zip 解压，里面就是 word/document.xml 这些文件）。“用什么字体画出来”的决定，是在你双击打开文档的那一刻，由 Word / WPS / LibreOffice 各自的渲染引擎做出的——同一份文档在不同电脑上打开，字形还可能不一样，因为“缺字体时用什么代替”是每个阅读器自己的选择。

那为什么你删掉重打就“正常”了？因为你打字时，编辑器会按你输入法的语言给新文字配好“成对”的字体：中文输入法下敲出的中文，eastAsia 通道会被明确指定，整行字于是统一。而 agent 生成的 XML 里，中文走的是“主题回退”的间接路径。两条路径，两种结果～

还有个更隐蔽的：不光数字和中文是两种字体，汉字和汉字之间看起来也可能怪怪的——AI 写的文档里，“与”字底下那一横拉得老长、出了头，自己打就不会。这不是 AI 写错了字：中文被回退到宋体后，“与”用的是宋体传承下来的老写法，底横出头；你平时用的黑体系字体里，底横是收住的。同一个字换个字体就换副长相，详见《同一个“与”字，为什么换个字体底横就出头了》。
