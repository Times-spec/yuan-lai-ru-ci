健康检查与优雅停机

上线不丢请求，下线不杀进程
👀 日常场景

发布新版本时，旧容器被直接杀掉，正在支付的用户当场报错。健康检查像「体检」：K8s 定期问服务「你还好吗」，答不上来就摘掉流量；优雅停机像「交接班」：收到下线信号后，先拒绝新请求，把手头的处理完再退出——用户毫无感知。

原理：它是怎么运作的

💡 探针持续报告服务是否可用，优雅停机让旧实例处理完手头请求再退出。

先看全过程

  1. 应用暴露 /health 存活探针
  2. 暴露 /ready 就绪探针
  3. 编排系统定期探测
  4. 探针失败：摘流量/重启
  5. 收到 SIGTERM 停止接新请求
  6. 处理完手头请求再退出

滚动发布时如果没有健康检查，新版本还没启动完就接流量，用户看到一堆 502；旧版本被 SIGKILL 直接杀掉，正在处理的支付请求就断了。两个探针分工不同：liveness（存活）答不上来说明进程僵死了，K8s 会重启它；readiness（就绪）答不上来说明暂时不能接流量（刚启动、依赖还没好），K8s 先把它的流量摘掉，好了再加回来。

优雅停机处理的是「下线」那一刻：收到 SIGTERM 后，应用先告诉网关「别再给我新请求」，等手头的请求处理完（设个上限如 30 秒）、关闭连接池、刷完日志，再退出。Node 要监听 SIGTERM，Java 靠 Spring 的 graceful shutdown，Go 用 signal.Notify。

探针接口一定要轻：/health 只返回 200，别在里面查数据库——数据库一抖，所有实例被同时摘掉，雪崩就是这么来的。

开发者：应该如何接入

  • K8s 探针：liveness/readiness 标准机制
  • Spring Boot Actuator：Java 生态开箱即用的健康端点
  • 自定义心跳：简单 HTTP 接口 + 外部监控
  1. 应用里加 /health 接口，只做轻量自检
  2. 区分 liveness（进程活着）和 readiness（能接流量）
  3. K8s deployment 里配置两个探针的路径和阈值
  4. 代码里监听 SIGTERM，实现优雅停机逻辑
  5. 设置 terminationGracePeriodSeconds 给足退出时间
  6. 发布时观察：先摘流量、再停旧版，错误率无抖动

相关条目

  • 探针：给服务装“心跳监测” 服务是死是活，探针说了算
  • Nginx 反向代理 所有请求，先过它这一关
  • DOH：加密的 DNS 查询 把查域名的请求，装进加密信封
