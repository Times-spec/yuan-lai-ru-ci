Linear/Jira：需求的任务看板

一个需求从出生到上线的旅行记录
👀 日常场景

产品经理在群里说：“登录页加个记住我，下版本上。”两周后功能上线了。这中间发生了什么？谁排的期、谁开发的、测了哪几轮、为什么延期两天——答案不在聊天记录里，而在一张叫 issue 的卡片上。Linear 和 Jira 就是管这些卡片的工具。

原理：它是怎么运作的

💡 把每件事变成一张有状态的卡片，需求从提出到上线的全过程都在卡片上留痕、可追溯。

先看全过程

  1. 产品经理创建一个需求卡片
  2. 写清背景、验收标准和优先级
  3. 需求进入迭代，分配给开发
  4. 开发认领，关联代码分支
  5. 测试按验收标准逐条验证
  6. 验证通过，上线并关闭卡片

这类工具的学名叫 Issue Tracker（问题跟踪器），核心思想只有一句：把“要做的事”变成一张有状态的卡片。

每张卡片都有标题、描述、负责人、优先级、截止日期，更重要的是“状态机”：待办 → 进行中 → 待验收 → 已完成。状态流转留下完整时间线，谁什么时候接手、为什么延期、最终怎么解决的，全都可查。产品经理提的“登录页加个记住我”，从提出、评审、排期、开发、测试到上线，经历的每一步都在卡片上留痕。

Jira 是老牌霸主，功能极重：自定义工作流、审批流、燃尽图，大公司爱它；代价是配置复杂，新人要学一阵。Linear 是新锐，哲学是“快”：键盘操作行云流水、界面干净，初创团队爱它。选哪个不重要，重要的是团队养成“事事有卡、卡卡有主”的习惯——口头说的需求会丢，聊天记录会沉，只有卡片是团队的共同记忆。

我该怎么用它

  • 先看懂三列看板：待办 → 进行中 → 已完成。所有工作都在这三列里流动，一眼看清团队在忙什么、卡在哪。
  • 一张卡只讲一件事：标题说清“做什么”，描述写清“为什么”和“做到什么程度算完”。一卡多事等于没卡。
  • 状态随手更新：开工拖到“进行中”，做完拖到“待验收”。看板是活的，状态不更新，看板就是死的。
  1. 接到任务先建卡：标题说清“做什么”，别写“做个登录”这种谜语
  2. 描述里写清背景、验收标准、优先级——这是以后扯皮的依据
  3. 开工了，把卡拖到“进行中”，指定负责人和截止日
  4. 开发时关联代码分支，合并后状态自动流转
  5. 做完拖到“待验收”，按验收标准逐条验
  6. 验证通过，关闭卡片——它成了团队可检索的记忆
