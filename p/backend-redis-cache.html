Redis 缓存

内存里的闪电仓库，App 秒开的秘密
👀 日常场景

双11零点抢券，几十万人同时涌入，App 却依然秒开；刷短视频时点赞数、评论数瞬间更新。这些高频读写的数据并没有每次都去查硬盘里的数据库，而是放在 Redis 这台「内存仓库」里——内存读写比硬盘快上千倍，这就是大多数 App 快的原因。

原理：它是怎么运作的

💡 把热点数据放进内存，用微秒级读写扛住数据库扛不住的高并发。

先看全过程

  1. 用户请求打到后端服务
  2. 先去 Redis 内存里查
  3. 命中：微秒级直接返回
  4. 没命中：查数据库
  5. 把结果写回 Redis 设过期
  6. 下次同样请求直接命中

Redis 快，第一个原因是它把数据全放在内存里。传统数据库的数据在硬盘上，查一次要经历寻道、读盘，毫秒级起步；内存随机访问是纳秒级，差距上千倍。第二个原因是它的网络模型：单线程处理命令配合 IO 多路复用（epoll，一种「一个线程同时盯着上万个连接」的技术），避免了线程切换的开销，单机就能扛住十万级 QPS。

典型用法叫「缓存旁路」：读时先查 Redis，没有再查数据库并回填；写时先更新数据库再删除缓存（而不是更新缓存，避免并发下的数据错乱）。配套的过期时间（TTL）让数据自动失效，防止内存被撑爆。

但缓存有三座大山：缓存穿透（查根本不存在的数据，每次都打到数据库，用布隆过滤器或缓存空值挡）、缓存击穿（某个热点 key 突然过期，大量请求同时打穿数据库，用互斥锁让只有一个请求去重建）、缓存雪崩（大批 key 同时过期，错开过期时间加随机值）。Redis 本身不是银弹，它通过 RDB 快照和 AOF 日志做持久化，但定位依然是「快而不一定最可靠」，核心数据永远以数据库为准。

开发者：应该如何接入

  • 自建 Redis：开源免费，一台服务器就能跑
  • 云 Redis（阿里云/腾讯云）：托管高可用，自动备份扩容
  • Redis Cluster：官方分片集群，数据分散到多节点
  1. 选部署方式：开发用 Docker 一行拉起，生产建议云托管
  2. 确定缓存策略：哪些数据进缓存、过期时间多长
  3. 代码里实现缓存旁路：先查缓存，未命中查库回填
  4. 设置合理的 maxmemory 和淘汰策略（如 allkeys-lru）
  5. 给 Redis 设密码，绝不把 6379 端口暴露到公网
  6. 加上监控：命中率、内存使用、慢查询
