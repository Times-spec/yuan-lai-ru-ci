对象存储：无限容量的云网盘

网盘背后的无限硬盘
👀 日常场景

你在 App 里上传头像、发朋友圈照片，这些文件并没有存在应用服务器的硬盘上——服务器硬盘才多大？它们被扔进了对象存储：一个理论上无限大、按用量付费的「云硬盘」，通过 HTTP 链接随时存取。

原理：它是怎么运作的

💡 用 HTTP 存取文件的海量存储，按量付费，文件直传直取不经过应用服务器。

先看全过程

  1. 后端向对象存储申请上传凭证
  2. 把带签名的上传 URL 给前端
  3. 前端直传文件到对象存储
  4. 存储返回文件的访问 URL
  5. 后端只在数据库里存 URL
  6. 用户访问时直接从存储拉取

对象存储和你电脑硬盘的组织方式完全不同：没有文件夹层级（看到的「文件夹」只是 key 的前缀），每个文件是一个「对象」，用唯一的 key 存取，元数据和内容分离。这种扁平结构让它可以无限横向扩展。

对开发者最大的改变是「直传」：传统做法是文件先传到应用服务器，服务器再转存，又慢又占带宽；现在后端只签发一个带过期时间的上传 URL，前端直接把文件 PUT 到存储，应用服务器完全不经手流量。下载同理，用户拿到的就是存储的 CDN 链接。

费用按「存储量 + 流量 + 请求次数」算，小文件高频读写反而可能比服务器硬盘贵。私有文件用签名 URL 控制有效期，公开读的 bucket 一定要关掉公共写入，否则第二天账单会教你做人。版本控制是另一个杀手锏：开启后每次覆盖都保留历史版本，误删文件可以找回，代价是存储量翻倍，记得配生命周期规则自动清理旧版本。

网站的图片到底存在哪

  • 对象存储：OSS / S3 / COS：文件扔进云存储，返回一个 URL，图片从存储直接发给用户
  • 服务器本地硬盘：文件存在应用服务器的硬盘上，和代码放一起
  • CDN 回源到对象存储：对象存储 + CDN：热门图片缓存到离用户最近的节点
  1. 你在 App 里点上传，图片先到应用服务器
  2. 服务器把它转存进对象存储（OSS/S3/COS）
  3. 存储返回一个永久 URL，服务器只存这个 URL
  4. 别人打开页面，图片直接从存储或 CDN 加载
  5. 应用服务器从此不再经手图片流量
