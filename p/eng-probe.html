探针：给服务装“心跳监测”

服务是死是活，探针说了算
👀 日常场景

你部署了一个新服务，上线 5 分钟就“假死”了：进程还在，端口也开着，就是不处理请求。监控看 CPU 内存都正常，人工重启才恢复。如果有个“探针”每隔几秒敲门问一句“你还活着吗”，它早就该被发现了。

原理：它是怎么运作的

💡 探针是外部系统定期发起的健康检查：存活探针判断进程要不要重启，就绪探针判断能不能接流量，启动探针给启动慢的服务宽限期。

先看全过程

  1. 探针=定期敲门检查
  2. 存活探针：死了就重启
  3. 就绪探针：没好就不接客
  4. 启动探针：给慢启动宽限
  5. 检查方式：HTTP/TCP/命令

在 Kubernetes 里，kubelet 就是靠探针管容器的。livenessProbe（存活探针）定期请求比如 GET /healthz，连续失败几次就重启容器——专治“假死”（进程活着但不干活）。readinessProbe（就绪探针）决定这个 Pod 要不要进负载均衡池：刚启动、正在加载数据时，先别接客。startupProbe（启动探针）给启动慢的应用（比如 Java 大应用）一个宽限期，宽限期内存活探针不生效，避免“还没启动完就被杀掉”的惨剧。

检查方式三种：HTTP GET 最常用，TCP 建连最轻量，容器里执行命令最灵活。探针的思想很通用：不要相信进程“看起来活着”，要定期验证它“真的能干活”。这也是你做发布验收时要“实测”而不是“看日志”的原因——日志会说谎，探针不会。

探针是怎么发现假死的

  • HTTP 探针：GET /healthz，返回 200 算活
  • TCP 探针：端口能连上算活
  • 命令探针：容器里跑条命令，退出码 0 算活
  1. 给服务加个 /healthz 接口
  2. 配存活探针：连续 3 次不通就重启
  3. 配就绪探针：没 ready 不进流量池
  4. 启动慢的服务再加启动探针宽限
  5. 探针间隔别太密：别把服务问死了
