点选/九宫格图像验证

“请点选所有红绿灯”，考的是语义理解
👀 日常场景

勾选“我不是机器人”之后，弹出一组九宫格图片：“请点击所有包含红绿灯的图片”。你一张张点过去，点完它又换一批：“再选出所有斑马线”。三轮下来你开始怀疑人生——这到底在验证谁？

原理：它是怎么运作的

💡 用人类擅长、机器曾不擅长的图像语义理解做门槛，叠加点选行为分析。

先看全过程

  1. 服务端下发一组待识别图片
  2. 用户按语义要求点选目标图片
  3. 记录点选顺序、坐标和耗时
  4. 服务端比对答案并分析行为
  5. 答错或行为异常就换题重来
  6. 多次失败升级为更难的挑战

九宫格验证的逻辑是：识别“这张图里有没有红绿灯”对人类是本能，对早期的机器却是难题——它需要语义理解，而不只是像素匹配。每道题的答案由服务端预先标注或众包（有意思的是，你答的题本身也在帮服务商标注训练数据，这就是 reCAPTCHA 当年顺带数字化书籍的思路）。除了答对，系统还会记录你的点选行为：点的顺序、每次点击的坐标落点、两题之间的间隔。真人点选会有犹豫和修正，脚本则往往是瞬间按固定坐标连点。现在图像识别 AI 进步很快，纯语义题的门槛在降低，所以这类验证越来越依赖“行为+语义”的组合拳：题目本身拦住简单脚本，行为分析拦住高级脚本，而持续换题、动态难度则让打码平台（雇真人代答的黑产）的成本居高不下。攻防的天平还在倾斜：随着多模态大模型普及，纯图片语义题的寿命越来越短，行业共识是把它退化为“二级挑战”，一线防御交给无感的行为评分。

网站该如何接入

  • Google reCAPTCHA v2 图片挑战：v2 高风险时自动弹出的图片挑战，生态最成熟。
  • hCaptcha：隐私友好的 reCAPTCHA 替代品，同样有点选挑战。
  • 极验点选验证：国内方案，中文语义题库更贴合国内用户。
  1. 选择服务商并在后台创建站点，获取 site key（前端用）和 secret key（后端用）。
  2. 前端加载服务商 SDK 并渲染验证组件，用户完成点选后拿到 token。
  3. 前端把 token 随表单提交到后端。
  4. 后端调用服务商的 siteverify 类接口，用 secret key 校验 token 真伪和时效。
  5. 校验通过后再放行登录/注册等业务动作。
  6. 记录验证失败率，异常升高时排查是否被针对性攻击。
