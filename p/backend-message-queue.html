后端基建

消息队列

秒杀不崩的幕后功臣
👀 日常场景

秒杀开始的瞬间，一百万个下单请求涌进来——如果直接打数据库，数据库当场去世。消息队列像一个巨大的「蓄水池」：请求先进队列排队，后端服务再不紧不慢地一个个处理，洪峰就这样被削平了。

原理：它是怎么运作的

💡 生产者只管往队列扔消息，消费者异步处理，削峰填谷、解耦系统。

先看全过程

  1. 秒杀请求瞬间涌入
  2. 请求先进入消息队列排队
  3. 立即返回「排队中」给用户
  4. 消费者按处理能力取消息
  5. 逐个扣库存、下单、通知
  6. 处理完确认，失败可重试

消息队列做三件事：削峰、异步、解耦。削峰是把瞬时洪峰摊平到时间轴上；异步是让用户不用等慢操作（发短信、生成报表扔进队列就返回）；解耦是让上下游不用互相等待——订单服务只管发「下单成功」消息，库存、物流、通知各自订阅，谁挂了都不影响下单。

代价是系统从「同步确定」变成「最终一致」：消息可能重复投递（网络超时重试），消费者必须做幂等（同一条消息处理多次结果不变）；消息也可能乱序，对顺序敏感的业务要按 key 分区。

选型看场景：RabbitMQ 功能全、路由灵活，适合业务解耦；Kafka 吞吐恐怖、消息可回放，适合日志和大数据；Redis Stream 轻量，适合已经有 Redis 的小团队。云厂商的消息队列则省掉运维。消息的投递语义分三种：至多一次（可能丢）、至少一次（可能重复）、恰好一次（最难实现）。业务选型时先想清楚自己能接受哪种，再决定幂等和去重的投入。

开发者：应该如何接入

  • RabbitMQ：功能最全，路由、延迟队列开箱即用
  • Kafka：百万级吞吐，消息可持久化回放
  • Redis Stream：轻量，复用已有 Redis
  1. 梳理链路：哪些操作可以异步（发短信、扣库存、记日志）
  2. 选型并部署 MQ，创建交换机/主题和队列
  3. 生产者发送消息，只带必要字段和业务 ID
  4. 消费者实现幂等：用业务 ID 去重
  5. 配置重试和死信队列，失败消息有地方查
  6. 监控积压量，积压告警就是扩容信号
