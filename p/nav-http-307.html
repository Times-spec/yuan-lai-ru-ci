HTTP 307/308 严格重定向

跳转也不改请求方法，POST 还是 POST
👀 日常场景

在手机银行 App 里提交一笔转账，页面跳转到“处理中”再跳到结果页，刷新结果页却不会重复扣款。这类“带着请求体一起搬家”的跳转，靠的就是 307/308：它们是 301/302 的严格版。

原理：它是怎么运作的

💡 307（临时）/308（永久）是 301/302 的严格版：跳转时必须原样保留请求方法与请求体，POST 跳过去还是 POST。

先看全过程

  1. 客户端发出 POST 请求
  2. 服务器返回 307/308 和新地址
  3. 客户端用同样方法重发请求
  4. 请求体原样带到新地址
  5. 307 临时、308 永久可被缓存

301 和 302 有个历史遗留问题：规范说跳转时要保持原请求方法，但早期浏览器都把 POST 改成了 GET。大家将错就错用了十几年，直到 API 时代才发现麻烦大了——支付、提交表单这类带请求体的 POST，一旦被改成 GET，请求体就丢了。于是 307 和 308 被发明出来，规则只有一条：严格保持原样。307 是 302 的严格版（临时），308 是 301 的严格版（永久、可缓存）。服务器返回 307/308 后，客户端必须用同样的方法、带着同样的请求体再发一次。它们最常见的出场是 API 网关做域名迁移或版本切换：老接口地址 308 到新地址，调用方的 POST 数据原样送达。要注意两点：一是非常老的客户端可能不认识 308，会当成错误；二是 308 和 301 一样会被缓存，配错了一样难收回，先用 307 验证没问题再换 308。

服务端该怎么配

  • API 网关转发：Kong、APISIX、Nginx 按规则把请求转发到新后端
  • Express res.redirect(307)：服务端代码里显式指定 307/308
  • Nginx return 307/308：网关层统一处理，配置即生效
  1. 确认跳转前后请求方法与请求体必须一致（如支付、表单接口）
  2. 临时用 307，永久迁移用 308
  3. 用 curl -X POST -d 做测试，检查跳转后仍是 POST
  4. 确认客户端（App、旧 SDK）支持 307/308 跟随
