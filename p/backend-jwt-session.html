JWT vs Session：两种登录态

登录状态，到底存在哪儿？
👀 日常场景

登录 App 后关掉再打开，不用重新登录——这个「记住我」的状态存在哪？两种主流做法：Session 把状态存在服务端，Cookie 里只放一把钥匙；JWT 则把用户信息直接写进 Token，服务端啥也不存。各有利弊，选错架构会返工。

原理：它是怎么运作的

💡 Session 状态存服务端、凭钥匙认人；JWT 把身份自包含在 Token 里，无状态但难撤销。

先看全过程

  1. 用户提交账号密码
  2. Session：服务端存状态发钥匙
  3. JWT：签发含用户信息的 Token
  4. 后续请求携带钥匙或 Token
  5. 服务端验钥匙查状态/验签名
  6. 通过则放行，失败跳登录

Session 是「认钥匙」模式：登录成功后服务端在内存/Redis 里存一份 {sessionId: 用户信息}，Cookie 里只放 sessionId。每次请求带着钥匙来，服务端查表认人。好处是随时可撤销（删掉那条记录就下线），坏处是服务端要存状态，多台机器要共享 Session（放 Redis）。

JWT（JSON Web Token）是「认章」模式：Token 分三段，中间那段直接写着用户 ID 和过期时间，服务端用密钥签名盖章。请求带着 Token 来，服务端验签名即可，不用查任何存储——天然适合分布式和 App。但代价是「发出去就收不回」：Token 在过期前一直有效，想踢人下线只能搞黑名单（又有状态了）或等过期。

实战组合拳：短有效期 access_token（15 分钟）+ 长有效期 refresh_token（7 天，存服务端可撤销）。敏感操作（改密码、支付）强制重新验证身份，别只信 Token。

🌀 如果没有它会怎样

没有登录态机制，你每点开一个页面都要重新输一次密码：HTTP 本身不记人，是 Cookie 里的钥匙、或 Token 上的「章」，替你向服务器证明「还是刚才那个人」。

🚫 常见误解

JWT 里存了用户信息，所以比 Session 更安全。其实正相反：JWT 发出去在过期前收不回，想强制下线还得额外搞黑名单；Session 删掉一条记录，就能立刻把人踢下线。

该怎么选

  • Session + Redis：状态存在服务端，Cookie 里只放钥匙；随时可踢人下线
  • JWT：身份自包含在 Token 里，服务端不用存状态，天然适合分布式
  • 组合拳：短 JWT + 长 refresh_token：15 分钟短命 Token 配 7 天可撤销的刷新令牌，兼顾体验和安全
  1. 先看架构：单体、机器少→Session 简单直接；服务多、有 App→JWT
  2. 再看需求：要不要“一键踢人下线”？要→Session，或 JWT+黑名单
  3. 定有效期：access_token 按分钟计，refresh_token 按天计
  4. 定存储：Token 放 HttpOnly Cookie（Web）或 Authorization 头（App）
  5. 写登出：Session 删服务端记录；JWT 要么等过期，要么维护黑名单
  6. 敏感操作（改密码、支付）：别只信 Token，加一步验证
