MySQL 索引

没有它，百万行查询要 10 秒
👀 日常场景

同样是查订单，有人一点筛选秒出结果，有人的后台转圈半天。差别往往就在索引上：加了索引的查询走「目录」定位，没加索引的只能逐行翻——一百万行数据，差距就是毫秒和十秒的区别。

原理：它是怎么运作的

💡 用 B+ 树给数据建「有序目录」，把全表扫描变成按目录定位。

先看全过程

  1. 查询条件里有 WHERE 字段
  2. 优化器检查该字段有无索引
  3. 有：沿 B+ 树逐层定位
  4. 叶子节点拿到数据位置
  5. 直接读取目标行返回
  6. 无：只能逐行全表扫描

索引的本质是「以空间换时间」的目录。InnoDB 的索引用 B+ 树实现：一种矮胖的多叉树，所有数据都存在叶子节点，且叶子节点按顺序连成链表。查数据时从根节点一层层二分定位，树高一般只有 3～4 层，意味着查上千万行数据也只需要 3～4 次磁盘 IO——而全表扫描要把每一行都读一遍。

聚簇索引（一般就是主键）比较特殊：叶子节点直接存着整行数据。普通二级索引的叶子节点只存「索引列 + 主键」，查到主键后还要回聚簇索引再查一次完整行，这叫「回表」。所以 SELECT * 会比只查索引列慢一截。

索引不是越多越好：每次写入数据都要同步更新所有索引，索引太多写操作会变慢，还占磁盘。经典口诀是「最左前缀」：联合索引 (a,b,c) 能服务 WHERE a=?、WHERE a=? AND b=?，但服务不了 WHERE b=?。建索引前先用 EXPLAIN 看执行计划，让数据说话。

开发者：应该如何接入

  • B-Tree 普通索引：最常用，适合等值和范围查询
  • 唯一索引：值不重复，自带去重约束
  • 全文索引：对文本内容做分词搜索
  1. 用慢查询日志或 EXPLAIN 找出慢 SQL
  2. 看 WHERE、JOIN、ORDER BY 里用到了哪些字段
  3. 给高频查询字段加索引，遵循最左前缀原则
  4. 上线前在测试库验证执行计划确实走了索引
  5. 定期用 EXPLAIN 复查，防止数据量变化后索引失效
