PRD：需求从这里开始

需求的出生证明
👀 日常场景

新功能开工前，产品经理甩过来一份几十页的文档：背景、目标、功能列表、验收标准全在里面。开发照着做，测试照着验，扯皮时翻出来“以文档为准”。这份文档就是 PRD——所有需求的出生证明，也是需求生命周期里最上游的一环。

原理：它是怎么运作的

💡 把“做什么、为什么做、做到什么程度算做完”写成团队唯一可信源，让产品、设计、开发、测试四方对齐。

先看全过程

  1. 写清背景与业务目标
  2. 定义目标用户与场景
  3. 拆成功能清单与优先级
  4. 补上非功能要求
  5. 定好验收标准
  6. 评审定稿，各方签字

PRD 的标准结构是：背景与目标、目标用户、功能需求（用户故事+流程图+原型链接）、非功能要求（性能、安全、兼容性）、验收标准、上线计划。它回答三个问题：做什么、为什么做、做到什么程度算做完。

一份好的 PRD 有三条标准：第一，讲清 why 而不只 what——开发知道“为什么”，才能在实现时做出正确的取舍；第二，可验收——每条需求都能写出对应的测试用例，“尽快”“尽量”这种词是事故源头；第三，无二义——不同人读出同一个意思。

它在需求生命周期里处在最上游：PRD → 交互设计 → 视觉设计 → 开发 → 测试，任何一环有疑问都回头查 PRD，扯皮时“以文档为准”。注意 PRD 不是实现方案：写“用什么技术、怎么实现”是越俎代庖，会限制开发的解法空间——产品定目标，技术定路线。

轻量团队可以用“一页纸 PRD”加原型代替几十页文档，但“目标”和“验收标准”这两块不能省：没有目标，评审时人人凭感觉；没有验收标准，上线时人人凭良心。

我该怎么写 PRD

  • 先写“为什么做”，再写“做什么”：开发知道“为什么”，才能在实现时做出正确的取舍。只写“做什么”的 PRD，开发只能照抄。
  • 用户故事句式：“作为…我想要…以便…”。逼你站在用户角度想，而不是罗列功能。
  • 验收标准必须可测试：“体验流畅”是废话，“列表滑动帧率≥55fps”才能验收。每条需求都要能写出对应的测试用例。
  1. 写背景和目标：不解决什么问题，就别立项
  2. 定义目标用户和场景：谁在什么情况下用
  3. 拆成功能清单，每个标优先级：P0 必须有，P1 有更好
  4. 每条功能写验收标准：可量化、可测试
  5. 拉上开发、设计、测试一起评审，当场拍板
  6. 需求变了走变更流程，同步更新 PRD，别让它和代码渐行渐远
