CSRF Token：表单里的防伪暗记

表单里那个看不见的隐藏字段，是防“被代表”的
👀 日常场景

你登录着银行网站，又手贱点开一封陌生邮件里的链接，页面一闪而过。还好钱没少——因为那个恶意页面偷偷替你提交的转账请求，缺了一个它永远拿不到的东西。而你压根没察觉，这场攻防其实已经发生过了。

原理：它是怎么运作的

💡 服务端发高熵随机 token 与会话绑定；攻击者能“替你发请求”，但读不到你页面的 token。

先看全过程

  1. 用户登录后服务端生成随机 token
  2. token 与用户会话绑定存服务端
  3. 随表单隐藏字段或响应头下发
  4. 前端提交时把 token 带回
  5. 服务端比对：缺 token 或对不上就拒绝
  6. 攻击者跨站读不到 token，伪造失败

CSRF（跨站请求伪造）攻击利用了一个浏览器的“热心肠”：你登录银行后，浏览器会自动在每个发往银行的请求里带上 Cookie。攻击者于是诱导你访问他的恶意页面，页面里藏着一个自动提交的表单，指向银行的转账接口——浏览器很“热心”地带上了你的登录 Cookie，银行以为是你本人在操作。CSRF Token 破解这个局的关键是同源策略：恶意页面虽然能“替你发请求”，但它读不到银行页面的内容，也就拿不到藏在银行表单里的那个随机 token。服务端在你登录时生成一个高熵随机串，和你的会话绑定，每次渲染表单时塞进隐藏字段；收到请求时检查 token 是否存在且匹配，不匹配直接拒绝。现代纵深防御还叠了三层：Cookie 设 SameSite=Lax/Strict（跨站默认不带 Cookie）、校验 Origin/Referer 头、检查 Sec-Fetch-Site 头。注意 CSRF Token 防的是“跨站伪造”，防不住 XSS——如果攻击者能在你的页面里执行脚本，他就能直接读 token，所以两类漏洞要分别修。

开发者：应该如何接入

  • Django / Rails 内置 CSRF 中间件：框架自带，开箱即用的同步令牌模式。
  • Flask-WTF / Spring Security：各自生态的 CSRF 防护组件。
  • SameSite Cookie + 头校验：纵深防御层，配合 token 使用。
  • 前后端分离：双提交 Cookie：token 放 Cookie，前端读出来再放进自定义头。
  1. 开启框架的 CSRF 中间件，或自研：登录后生成随机 token 存 session。
  2. 服务端渲染的每个表单里加入隐藏字段 <input type="hidden" name="csrf_token" value="...">。
  3. 前后端分离项目：后端把 token 写进 Cookie，前端 JS 读出后放进 X-CSRF-Token 请求头。
  4. 后端中间件校验：请求中的 token 与 session 中的比对，不一致返回 403。
  5. 登录态 Cookie 设置 SameSite=Lax，关键操作接口再校验 Origin/Referer。
  6. token 随会话生命周期轮换，登出即销毁，不搞全局固定 token。
