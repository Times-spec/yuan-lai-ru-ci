IP 限流

“操作频繁请稍后再试”背后的看门人
👀 日常场景

连续点好几次“获取验证码”，页面弹出“操作频繁，请 60 秒后再试”。抢购时疯狂刷新，突然被请去“排队”。这些“不让点”的时刻，背后都站着同一个看门人。它不看你是谁，只看你点的有多快。

原理：它是怎么运作的

💡 令牌桶/滑动窗口算法按 IP·账号维度计数，超阈值直接拒绝或加验证。

先看全过程

  1. 每个请求按 IP/用户/接口维度计数
  2. 令牌桶或滑动窗口算法判定频率
  3. 正常频率：直接放行
  4. 超阈值：拒绝或要求人机验证
  5. 计数器随时间自动衰减恢复
  6. 多维度叠加：IP+账号+接口三级

限流的本质是“用规则区分正常人和脚本”：正常人点“获取验证码”一分钟点一次，脚本一秒点十次。常用算法有三种：固定窗口（每分钟最多 N 次，简单但边界有毛刺）、滑动窗口（精确统计过去 60 秒，更平滑）、令牌桶（桶里有 N 个令牌，请求消耗令牌、令牌按速率补充，能容忍短暂突发）。工程上一般用 Redis + Lua 脚本做原子计数，保证高并发下计数准确。限流的维度是门学问：只限 IP 会误伤公司/学校出口同 IP 的正常用户，只限账号防不住换号攻击，所以成熟做法是 IP、账号、接口三级叠加，超了先上验证码挑战而不是直接封禁——把“可疑”变成“去证明你是人”，而不是一棍子打死。短信接口是限流的重灾区：阿里云默认就是 1 条/分钟、5 条/小时、10 条/天，不配限流的短信接口等于给黑产送钱的提款机。

开发者：应该如何接入

  • Nginx limit_req：网关层限流，一行配置挡住大部分粗糙攻击。
  • Redis + Lua 计数：应用层精细限流，原子操作防并发穿透。
  • Cloudflare Rate Limiting：CDN 边缘限流，攻击流量到不了源站。
  • Kong / APISIX 限流插件：API 网关原生限流插件，可视化配置。
  1. 确定限流维度：短信/登录接口按“手机号+IP”双维度，其他接口按 IP 或用户。
  2. 选算法：防轰炸用滑动窗口，允许突发用令牌桶，通过压测定阈值。
  3. 用 Redis + Lua 实现原子计数（INCR+EXPIRE 一次完成），key 设 TTL 自动过期。
  4. 超限时返回 429 状态码 + Retry-After 头，前端据此做倒计时提示。
  5. 高风险接口超限后不直接封，加一道人机验证（滑块/短信）做缓冲。
  6. 限流日志进监控，阈值随业务增长定期复盘调整。
