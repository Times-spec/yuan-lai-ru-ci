OAuth 回跳：第三方登录最后一公里

去大厂认个证，带着暗号回来
👀 日常场景

点“使用微信登录”，页面跳到微信的授权页，你点同意后又跳回网站，而且已经是登录状态了。全程网站没碰过你的微信密码，密码只给微信看过。网站拿到的只是一张“他已验证”的凭证，干净又省心。

原理：它是怎么运作的

💡 标准 OAuth 2.0 授权码流程：网站把用户带到第三方授权页，用户同意后，第三方带着一次性授权码跳回 redirect_uri，网站后台再拿授权码去换用户信息。

先看全过程

  1. 网站拼好授权链接跳到第三方
  2. 用户在第三方页面点同意授权
  3. 第三方带授权码跳回本站
  4. 网站后台用授权码换令牌
  5. 用令牌拉用户信息完成登录

OAuth 授权码回跳是“登录外包”的标准动作，核心思想是：网站永远不碰你的第三方密码。流程分四步：网站先把你带到微信、Apple、Google 的授权页（URL 里带着自家身份 client_id、跳回地址 redirect_uri 和随机数 state）；你在第三方页面点同意；第三方带着一次性授权码 code 跳回你的 redirect_uri；你的服务器拿着 code 再加上绝不能泄露的 client_secret，去第三方后台换 access_token，最后用 token 拉取你的头像昵称，完成登录。为什么绕这么大弯？因为 code 是走浏览器前台传递的，可能被看见，所以它只能用一次、几分钟就过期；真正的令牌交换发生在服务器之间，浏览器接触不到。state 参数则是防 CSRF 的：回跳时必须原样带回，服务器校验不一致就拒绝，防止攻击者劫持别人的登录态。

开发者：应该如何接入

  • 微信开放平台（网站应用）：国内最常用的第三方登录
  • Sign in with Apple / Google Identity：国际通用，苹果要求上架 App 必须提供
  • Auth0 / Keycloak 自建：统一对接多家，自己掌控用户体系
  1. 在第三方开放平台创建应用，拿到 client_id 和 client_secret，登记 redirect_uri
  2. 登录按钮拼授权 URL：带上 client_id、redirect_uri、scope、随机 state
  3. 用户同意后，第三方 302 带 code 跳回你的 redirect_uri
  4. 后端用 code 加 client_secret 调 token 接口换 access_token
  5. 用 access_token 拉取用户信息，建本地账号并种登录态
