登录后回跳：回到你来的地方

登录完，送你回你本来要去的地方
👀 日常场景

你点开一篇付费文章，网站先把你拦到登录页，登录成功后却神奇地回到了那篇文章，而不是首页。这个“记住你从哪来”的机制，就是登录回跳。登录页像个尽职的门卫：先拦下你，办完手续再把你送回去。

原理：它是怎么运作的

💡 进入登录页前把原目标地址存进 redirect_uri 参数（或 session），登录成功后服务端读出它，用 302 把用户送回最初想去的地方。

先看全过程

  1. 未登录访问受保护页面
  2. 被 302 到登录页并带上原地址
  3. 用户完成登录
  4. 服务端取出原地址
  5. 302 跳回最初的目标页面

登录回跳解决的是“别让我白跑一趟”：你点开一篇付费文章，网站把你拦到登录页，登录完又把你送回那篇文章，而不是冷冰冰的首页。实现很直白：拦截未登录请求时，先把用户原本要去的地址记下来（放在登录页 URL 的 next 参数里，或存进 session），登录成功后读出来，用 302 跳回去。这套机制有个著名漏洞叫开放重定向：如果不对回跳地址做校验，攻击者可以构造“正经网站.com/login?next=钓鱼网站.com”这样的链接——用户在正经网站完成登录，放心地点了跳转，结果被送到一模一样的钓鱼页。所以铁律是：只允许跳回本站内的相对路径，或者校验域名白名单。第三方登录里的 redirect_uri，本质上就是这套机制的标准化版本。实现时还有两种存法：把原地址放在登录页 URL 的 next 参数里，简单但刷新会丢；存进服务端 session，稳但要多一次读写。App 里还要多想一步：登录成功后别让回退栈里还留着登录页，否则用户一点返回又掉回登录，形成死循环。

开发者：应该如何接入

  • URL 参数 next：登录页 URL 里带 ?next=原地址，最简单
  • Session 存储：原地址存服务端 session，不暴露在地址栏
  • OAuth redirect_uri：标准化方案，第三方登录都在用
  1. 拦截未登录请求，记下用户原本要访问的完整地址
  2. 跳登录页时把地址放进 next 参数或 session
  3. 登录成功后取出该地址准备回跳
  4. 校验地址：只允许本站内的相对路径或白名单域名
  5. 用 302 跳回，登录页本身不要留下历史记录
