小功能大智慧

分片上传/断点续传

大文件切成小块传，断了也能续上
👀 日常场景

上传一个 2GB 的视频，到 90% 时断网了。你以为要从头再来，结果重新上传时进度条直接从 90% 继续走——没传完的部分补上就行。网盘、视频网站上传大文件时，背后都是这套机制在兜底。

原理：它是怎么运作的

💡 前端用 Blob.slice 把文件切成小块并行上传，服务端按序号合并；已传分片被记账，续传时跳过。

先看全过程

  1. 计算文件哈希作为唯一标识
  2. Blob.slice 按固定大小切分
  3. 多个分片并发上传
  4. 服务端按序号暂存分片
  5. 断网后查询已传分片清单
  6. 跳过已传，只补传剩余分片

大文件上传最怕两件事：慢和断。分片上传同时解决两个。前端用 File 对象的 slice 方法（跟切蛋糕一样）把文件按固定大小（比如 5MB）切成 N 个小块，每个小块独立发一个上传请求，浏览器可以并发传 3～6 个，总耗时接近“同时传”，比一个一个排队快得多。断点续传的关键是一个“账本”：上传前先算整个文件的哈希值（MD5，一种给文件算“指纹”的算法）作为文件唯一标识，每传完一块，服务端就在 Redis 里记一笔；断网重连后，前端先问服务端“我这个文件传到哪了”，跳过已传的分片只补剩下的。还有个 bonus 叫“秒传”：如果哈希值在服务端已存在，说明别人传过一模一样的文件，直接跳过上传。下载方向的断点续传原理相通，靠 HTTP 的 Range 头（告诉服务器“我要从第几个字节开始”）和 206 状态码实现。标准化协议叫 tus，专门解决“传一半断了怎么办”。为什么分片大小要讲究？太小则请求数爆炸（1GB 按 1KB 切就是一百万个请求），太大则失败重试成本高，5MB 左右是常见折中。

网站是怎么做到的

  • Blob.slice：像切蛋糕一样切文件：浏览器用 File 对象的 slice 方法，把 2GB 的大文件按 5MB 切成几百个小块，每个小块独立上传。
  • 文件哈希：给文件办身份证：上传前先算整个文件的 MD5“指纹”。靠这个指纹，服务端认得出“这个文件传过一半了”，也认得出“这个文件别人传过”。
  • 记账本：哪块传了记哪块：每传完一块，服务端记一笔。断网重连后先查账本，只补没传的块，传过的跳过。
  • 秒传：别人传过你就不用传：哈希一查，服务端发现一模一样的文件已经在了，直接“秒传”成功，连 1 字节都不用上传。
  1. 你选中 2GB 视频，浏览器先算它的哈希指纹
  2. 拿指纹问服务端：这个文件传过吗？传到哪了？
  3. 没传过：按 5MB 切成几百块，3～6 个并发一起传
  4. 每传完一块，服务端在账本上记一笔
  5. 断网了！重连后先查账本，传过的块全部跳过
  6. 只补没传的块，全齐了服务端按序号拼好，校验哈希确认完整
