Token：大模型眼中的文字单位

模型眼里的文字，全是数字
👀 日常场景

API"按 token 计费""128K 上下文""数一数 token 别超了"——token 到底是什么？它不是字也不是词，而是一种折中的切分单位，模型眼里你的话全是一串数字。

原理：它是怎么运作的

💡 BPE 把文本切成子词再映射成数字 ID：高频词一个 token，罕见词拆开——模型看到的永远是数字。

先看全过程

  1. 原始文本进来
  2. BPE 按学到的规则切分
  3. 高频词：一个词一个 token
  4. 罕见词：拆成多个子词
  5. 每个 token 映射成数字 ID
  6. 模型实际看到的是 ID 序列

模型只懂数字，不懂汉字，所以第一步是把文字变成数字 ID。但怎么切是个 trade-off：按词切，词表会爆炸（新词无穷无尽）；按字切，序列又太长（注意力是 O(n²)，长序列贵得离谱）。

BPE（字节对编码）是个聪明的折中：从单个字符出发，反复把文本里最高频的相邻组合并成新 token。高频词如"学习"各自占一个 token，罕见词会被拆成几个子词。结果是常用内容又短又省、罕见内容也能表示，一个 5 万左右的词表就能覆盖几乎所有文本。

在逻辑链上，Token 是"文字进入数学世界"的第一道门：它承接"模型只懂数字"的现实，为后面的 Embedding、预训练铺好输入。一个冷知识：你付的 API 账单、128K 上下文窗口，计的都是 token 不是字；中文通常 1 个汉字约 1.5～2 个 token，所以中文用户调 API 天生贵一点、上下文也更不经用。

调用 API 时怎么省 Token

  • 提示词"减肥"：删掉寒暄和重复背景，一句话能讲清就别写三段，输出长度设上限
  • 提示缓存（Prompt Caching）：各家 API 提供的缓存：重复的系统指令只计费一次，后续调用打折
  • 小活小模型，大活用大模型：分类、打标签这类小判断用便宜模型，复杂推理再上旗舰
  1. 先搞清你用的模型 1 个汉字约几个 token（中文通常 1.5～2 个，比英文贵）
  2. 写提示词时做减法：背景只给模型真需要的，历史对话定期做摘要
  3. 系统指令又臭又长？查一下你用的 API 有没有提示缓存，开了能省一大截
  4. 长文档别整篇塞：先让模型分段摘要，再基于摘要问
  5. 给 max_tokens 设个上限，别让模型自由发挥写小作文
  6. 每月看一眼账单，按输入/输出 token 拆开看，钱花在哪一目了然
