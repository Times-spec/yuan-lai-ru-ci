搜索自动补全

你每敲一个字，背后都在查一遍
👀 日常场景

在淘宝搜“连衣裙”、在B站搜视频标题，你才敲了两三个字，下拉框里就冒出一串完整的搜索词：“连衣裙夏新款”“连衣裙碎花长裙”。点一下就能直达结果，连剩下的字都不用敲。你有没有想过，这些词到底从哪儿冒出来，又为什么总能猜中你想搜什么？

原理：它是怎么运作的

💡 把输入的前缀实时发给服务端，在海量词库里做前缀匹配加排序，返回候选列表即时展示。

先看全过程

  1. 用户输入字符触发输入事件
  2. 前端防抖等待输入停顿
  3. 取消上一次未返回的请求
  4. 请求接口发送当前关键词
  5. 服务端前缀匹配候选词
  6. 按热度与相关性排序返回

这件事是浏览器和服务器分工完成的。浏览器端监听输入框的 input 事件，但不会每敲一个字就发请求——而是做“防抖”（debounce，一种“等用户停手再执行”的技巧）：等你停顿约200～300毫秒才发一次，避免请求风暴；同时取消上一次还没返回的请求，防止慢请求的结果覆盖掉新输入。请求打到服务端的建议接口（比如 /api/suggest?q=连衣），服务端在词库里做前缀匹配。词库通常用前缀树（Trie，一种按字首组织词的树形结构）或 Elasticsearch 的 suggest 功能实现，毫秒级就能从上百万词里捞出候选。排序是关键：按搜索热度、你的历史偏好、地理位置加权，热词排前面。为什么这样设计？核心权衡是“快”和“准”：防抖省带宽、取消旧请求保正确、热度排序让你大概率在前三个候选中找到目标，少敲字就是省时间。注意，浏览器自带的表单自动填充（autocomplete 属性）和这是两回事：那只是记住你以前填过的内容，而搜索补全背后是一套实时查询服务。

网站是怎么做到的

  • 防抖：等你停手再发请求：你每敲一个字并不直接发请求，浏览器会等你停顿约250ms，确认你“说完了”才发一次——把一串击键合并成一次请求。
  • 作废旧请求：慢的别捣乱：每次发新请求前，先把上一发还没返回的请求取消掉。否则网速一抖，慢请求迟到了，反而把你新输入的正确结果覆盖掉。
  • 前缀树 Trie：百万词库毫秒级捞词：词库按字首组织成树形结构，输入“连衣”就顺着“连→衣”这条枝往下找，所有后缀一次捞出，根本不用全表扫描。
  • 排序才是灵魂：热度加权：捞出一堆候选后，按搜索热度、你的历史偏好、地理位置加权排序。猜中的秘诀不在“找到”，而在“把最可能的前三个放你眼前”。
  1. 你敲下字符，浏览器监听到输入框的 input 事件
  2. 但它不急着发请求——先等你停顿约250ms（防抖），确认你这一串字敲完了
  3. 同时把上一发还没返回的请求直接作废，防止慢结果覆盖新输入
  4. 请求打到服务端的 /suggest 接口，带上你输入的前缀
  5. 服务端在前缀树里顺着字首往下捞，一次捞出所有候选词
  6. 候选按热度、你的偏好、地域加权排序，前三个大概率命中，点一下直达
