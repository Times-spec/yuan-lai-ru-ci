分布式锁

多台机器，抢同一件事
👀 日常场景

三台服务器同时跑「清理过期优惠券」，如果都动手，同一批券会被清三遍。单机用 synchronized 就行，多台机器互不认识——这时需要一把「所有人都能看到的锁」，Redis 的原子命令就是这把锁的最佳载体。

原理：它是怎么运作的

💡 用 Redis 原子命令实现跨进程互斥，同一时刻只允许一个执行者。

先看全过程

  1. 抢锁：SET key 值 NX PX 原子执行
  2. 成功拿到锁：执行业务
  3. 没拿到：等待或直接放弃
  4. 业务完成：用 Lua 脚本释放
  5. 释放时校验值，防止删别人的锁
  6. 超时未完成：锁自动过期防死锁

分布式锁的本质是「找一个大家都信任的第三方来仲裁」。Redis 的 SET key value NX PX 10000 是原子操作：NX 表示「不存在才设置」（抢锁），PX 表示「10 秒自动过期」（防死锁，持有者挂了锁也不会永远卡住），两个动作一步完成，不存在抢到一半的中间态。

释放锁必须校验身份：只能删自己加的锁。做法是 value 存随机数，释放时用 Lua 脚本「比对 value 一致才删除」——Lua 在 Redis 里单线程执行，比对+删除不可分割，否则 A 的锁过期了，B 刚加上，A 一删就把 B 的锁删了。

看门狗（watchdog）解决「业务没跑完锁先过期」：后台线程定期续期。但这也意味着锁不是绝对可靠——Redis 主从切换时可能丢锁。对正确性要求极高的场景（资金），Redlock 多节点方案仍有争议，能用数据库唯一约束解决的，优先不用分布式锁。

开发者：应该如何接入

  • Redis SET NX：最常用，实现简单
  • Redisson：Java 客户端，看门狗自动续期
  • ZooKeeper/etcd：强一致，锁更可靠
  1. 选实现：简单场景手写 SET NX，复杂用 Redisson
  2. 加锁用 SET key 随机值 NX PX 超时，原子一条命令
  3. value 用 UUID，保证释放时能认出是自己的锁
  4. 释放用 Lua 脚本：校验 value 一致才 DEL
  5. 业务超时时间必须小于锁过期时间，或加看门狗续期
  6. 没抢到锁要有退路：重试几次或直接返回，不硬等
