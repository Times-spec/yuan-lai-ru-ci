MySQL 事务

转账不能只扣款、不入账
👀 日常场景

银行转账时如果系统在扣款后突然断电，钱不能凭空消失，也不能凭空多出来。事务就是数据库的「后悔药」机制：把多个操作打包成一个整体，要么全部成功，要么全部撤销，绝不留下半成品——这就是 ACID 里那个 A（原子性）在保驾护航。

原理：它是怎么运作的

💡 用 ACID 四性把一组 SQL 打包成原子操作，要么全成功，要么全回滚。

先看全过程

  1. BEGIN 开启事务
  2. 执行扣款、入账等多条 SQL
  3. 全部成功：COMMIT 提交
  4. 中途出错：ROLLBACK 回滚
  5. 回滚后数据恢复原样
  6. 其他会话看不到中间状态

事务解决的是「一组操作必须同生共死」的问题。ACID 是四个承诺：原子性（Atomicity，要么全做要么全不做）、一致性（Consistency，数据从一个合法状态到另一个合法状态）、隔离性（Isolation，并发事务互不干扰）、持久性（Durability，提交了就丢不了）。

实现上靠两种日志：undo log 记录「改之前的值」，回滚时按它恢复；redo log 记录「改了什么」，即使断电重启也能把已提交的数据找回来。隔离性则靠锁和 MVCC（多版本并发控制，一种「给每个事务看到不同版本数据」的机制）实现，代价是隔离级别越高并发越差。

默认的 REPEATABLE READ 能防脏读和不可重复读，但会有幻读（两次查询之间冒出新行）；SERIALIZABLE 最严格但性能最差。实战建议：事务尽量短，能 50 毫秒提交就别拖 5 秒——长事务持有锁不放，是线上死锁和慢查询的头号元凶。

开发者：应该如何接入

  • InnoDB 事务：MySQL 默认引擎，原生支持 ACID
  • 程序端事务管理：Spring @Transactional 等框架声明式事务
  • 分布式事务（Seata/XA）：跨库、跨服务的事务协调
  1. 确认表引擎是 InnoDB（MyISAM 不支持事务）
  2. 用 BEGIN 开启事务，业务 SQL 按顺序执行
  3. 全部成功则 COMMIT，有异常则 ROLLBACK
  4. 把事务边界收敛到最小：只包必须原子的操作
  5. 避免在事务里调外部接口、发 MQ——慢且不可回滚
  6. 压测观察锁等待，设置合理的 innodb_lock_wait_timeout
