JSON / YAML

机器爱 JSON，人类爱 YAML
👀 日常场景

前端调接口，返回的是一大坨 JSON；后端同事改 K8s 配置，打开的却是 YAML。你有没有想过：为啥接口不用 YAML？为啥配置文件不用 JSON？这两种长得有点像的格式，其实是为完全不同的“读者”设计的。

原理：它是怎么运作的

💡 JSON 是给机器读的数据交换格式，严格、简单、无歧义；YAML 是给人写读的配置格式，靠缩进和注释追求可读性。

先看全过程

  1. 2001 年前：XML 当道，但写起来又臭又长
  2. JSON 诞生：JS 对象字面量的严格子集
  3. Ajax 兴起，JSON 成接口通用语
  4. 人类写配置嫌 JSON 啰嗦：不能注释引号多
  5. YAML 登场：缩进定层级，原生支持注释
  6. 分工确立：机器用 JSON，人写 YAML

JSON 的全称是 JavaScript Object Notation，本质是“JS 对象字面量长得最像的那部分”：键值对、数组、字符串、数字、布尔、null，没了。它的设计哲学是“给机器看的”：语法极度严格（键必须双引号、不能写注释、末尾不能多逗号），换来的是任何语言都能用几十行代码写出解析器，且解析结果零歧义——这就是它统治 API 的原因。

YAML（“YAML Ain't Markup Language”）目标读者是“人”：用缩进表示层级（像 Python），原生支持注释，还支持锚点引用避免重复。Docker Compose、Kubernetes、GitHub Actions 的配置文件全是 YAML，因为运维每天要手写、手改，可读性就是生产力。

代价也很对称：JSON 的严格让手写很痛苦（少个逗号就全炸）；YAML 的灵活很微妙——缩进混用 Tab 和空格会炸，YAML 1.1 里 yes 会被解析成布尔值（著名的“挪威问题”）。记住这句：数据在机器之间跑，用 JSON；配置要被人天天改，用 YAML。

开发者：应该如何接入

  • JSON：REST API、前后端通信、package.json
  • YAML：K8s manifest、docker-compose.yml、CI 流水线
  • TOML：比 YAML 更简单明确的新兴配置格式
  1. 判断读者：是程序还是人，决定用 JSON 还是 YAML
  2. JSON 场景：定义接口契约，统一字段命名风格
  3. YAML 场景：统一用空格缩进（2 格），绝不混用 Tab
  4. 给 YAML 加 yamllint 或编辑器插件，提交前自动校验
  5. 对外暴露的配置示例，同时提供最小可用版本
