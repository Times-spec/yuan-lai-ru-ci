实时推送

不用刷新，消息自己“流”进来
👀 日常场景

看直播时弹幕一条条冒出来、股票行情数字自己跳动、客服对话框里对方的消息秒到——页面从头到尾没刷新过，新消息却自己出现了。这种“服务器主动找你”的能力，就是实时推送。

原理：它是怎么运作的

💡 服务端有新数据就主动推给浏览器：SSE 是单向的 HTTP 长连接，WebSocket 是全双工的双向通道。

先看全过程

  1. 浏览器发起连接请求
  2. 服务端保持连接不断开
  3. 有新数据时主动推送
  4. 前端收到后更新页面
  5. 断线自动重连恢复
  6. 心跳包检测连接是否存活

传统网页是“一问一答”：浏览器发请求，服务器回数据，不问就不给。但弹幕、聊天、行情这种场景等不起——总不能每秒刷新一次页面。于是有了“服务器主动推”。两条主流路线：SSE 和 WebSocket。SSE（Server-Sent Events，服务器发送事件）走的是普通 HTTP，服务器返回一个 text/event-stream 类型的响应然后不关闭连接，有新数据就往这个“水管”里写，浏览器用 EventSource 接收，自带断线重连，简单但只能单向（服务器→浏览器）。WebSocket 则是一次“升级”：先 HTTP 握手，约定 Upgrade: websocket，之后这条 TCP 连接就变成全双工（双方可随时发言），适合聊天、弹幕、协同编辑这种双向高频场景。为什么有新数据就能“秒到”？因为连接一直开着，省掉了每次“建立连接→发请求→等响应→断开”的开销。配套机制有三件套：心跳包（定期 ping/pong 证明还活着，顺便防中间代理掐掉空闲连接）、断线重连（指数退避，别一断就狂连把服务器冲垮）、消息去重（网络抖动可能导致重复推送）。

网站是怎么做到的

  • SSE：服务器的单向“水管”：走普通 HTTP，服务器返回一个不关闭的响应，有新数据就往“水管”里写。浏览器用 EventSource 接收，自带断线重连。
  • WebSocket：全双工对讲机：先 HTTP 握手约定升级，之后这条连接双方随时可发言。聊天、协同编辑这种“你来我往”的场景用它。
  • 心跳包：确认对方还活着：定时发一个极小的数据包探活。中间代理会掐掉长时间没动静的连接，心跳就是告诉它“我还用着”。
  • 断线重连：指数退避：断线后不是立刻狂试，而是 1s、2s、4s、8s 这样越等越久再试，避免把刚恢复的服务器又打挂。
  1. 你打开直播页，浏览器发起连接请求（SSE 或 WebSocket 握手）
  2. 服务端接受，但不关闭连接——这条“线”一直留着
  3. 有新弹幕了，服务端直接把数据推进这条连接
  4. 浏览器收到，立刻把弹幕渲染到页面上，全程无刷新
  5. 定时心跳包探活，确认连接还健在
  6. 网络一抖断线：按指数退避自动重连，回来后继续收消息
