API 网关：所有请求的统一入口

所有 API 的统一大门
👀 日常场景

App 要调几十个后端接口：用户、订单、支付……如果每个服务各自做鉴权、限流，代码重复得到处都是。API 网关站在所有服务前面当「总机」：统一验身份、统一限流，再按路径把请求分发到对的服务，后端只管写业务。

原理：它是怎么运作的

💡 统一处理鉴权、限流、路由转发，所有 API 先过网关再到业务服务。

先看全过程

  1. 客户端请求打到网关
  2. 网关校验 Token/签名
  3. 检查限流配额
  4. 按路由规则转发服务
  5. 聚合响应返回客户端
  6. 记录日志与监控指标

微服务拆分后，对外暴露几十个服务既混乱又危险：每个服务都要重复做鉴权、CORS、限流，前端还要记一堆域名。网关把这些「横切关注点」收拢到一处：请求先进网关，网关验身份、查限流、做路由，后端服务只收「干净」的内部请求。

网关和 Nginx 反向代理的区别在于「懂业务」：Nginx 主要做流量转发，网关还能做 JWT 校验、按用户限流、请求聚合（一次查用户+订单拼成一个响应给 App）、协议转换（HTTP 转 gRPC）。

但网关也是单点：它挂了所有服务都不可用，所以网关本身必须高可用部署；同时别把业务逻辑写进网关——网关一旦变成「大泥球」，每次改业务都要动网关，微服务的独立性就没了。网关选型还要看协议支持：REST 转 gRPC、WebSocket 长连接透传、按权重灰度发布，这些能力各家差异很大。建议先列出自己的必备清单再对比，别被漂亮的 demo 忽悠了。

开发者：应该如何接入

  • Kong：插件生态最丰富，Lua 可扩展
  • Apache APISIX：国产，性能强，动态路由
  • Spring Cloud Gateway：Java 生态无缝集成
  1. 梳理所有对外 API，统一收敛到网关域名下
  2. 选网关产品并高可用部署（至少 2 节点）
  3. 配置路由规则：/api/user/* 转用户服务
  4. 接入鉴权插件：校验 JWT 或 API Key
  5. 按用户/接口配置限流阈值
  6. 接监控告警，网关延迟升高第一时间知道

相关条目
